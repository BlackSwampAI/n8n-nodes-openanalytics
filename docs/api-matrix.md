Released Open Analytics v0.8.0 API keys are site-bound credentials generated per site in Settings → API. Those key-authenticated queries are scoped to the key site, and the server rejects `X-OA-Site` for API-key authentication. The separate Revenue OAuth2 path sends an explicit Site ID; the server checks `revenue:read`, a user principal, live membership, and owner role. These details are verified against release source and do not establish hosted or other self-hosted deployments.

For each ordinary REST operation, begin with declarative routing and record which routing, expressions, pagination, `preSend`, or `postReceive` behavior implements its contract. Revenue uses declarative routing plus a pagination callback as an error boundary: it calls the pinned n8n `makeRoutingRequest` once, retaining native credential auth, response conversion, and paired-item lineage. n8n may make a separate token-refresh HTTP request internally; one callback invocation does not mean one total network request. The node does no manual token or HTTP handling. This behavior is source-reviewed against n8n stable commit `dcba26c8a530d63041cd8298b8b30295d5476f6f`; the OAuth path has not been exercised in a live editor. A programmatic row must identify the concrete requirement that declarative routing cannot safely express, such as a trigger, GraphQL/non-REST protocol, external runtime dependency, incoming-data transformation, or full node versioning. Generic "weird JSON" is not an exception.

Also verify path encoding, identifiers and response wrappers, list pagination, empty behavior, errors, update preservation, and edition boundaries. Prefer current documented routes; record pinned-version compatibility differences explicitly. Do not advertise an operation solely because it exists in OpenAPI.

## Template source hygiene

Registered source and compiled modules must expose one case-exact filename-derived constructible export. The smoke rejects redundant constructor aliases as template hygiene; n8n's loader selects the filename-derived export key. AST review rejects property files that contain only empty typed `INodeProperties[]` placeholders and import/type scaffolding. Remove one only after checking the assembled node description and proving shared parameters and routing retain operation visibility, required controls, request construction, and output handling. Ordinary requests use JSON; multipart examples require evidence before adding custom execution code.

## Revenue authentication evidence and limits

Released Open Analytics v0.8.0 (`a07da7020810d3a975524daad2a544c9205ea65e`, 2026-09-19; latest stable release rechecked 2026-10-07) scopes API keys to one site, rejects `X-OA-Site` on API-key requests, and cannot mint `revenue:read` for API keys. Revenue requires `revenue:read`, a user principal, a canonical site UUID, live membership, and the owner role. OAuth2 is therefore an additive Revenue-only path; the server enforces scope and current membership. `currency` remains routed to preserve saved workflow shape, but v0.8.0 ignores it and reads the site's reporting currency ([analytics service source](https://github.com/OpenLabs-so/openanalytics/blob/a07da7020810d3a975524daad2a544c9205ea65e/apps/api/src/analytics/service.ts)).

Upstream main reviewed on 2026-10-05 at `f7fc9169f32d48e55eb9106bceae9e87b6aa6bb9` is seven commits ahead of the release and its compared authentication files show no relevant change. This is separate source evidence, not proof of deployed hosted behavior. No hosted API calls or real n8n editor smoke were performed. Other versions and self-hosted installations remain unverified. The public API reference examples also use `X-OA-Site`; released key handling rejects that header when using an API key. The release middleware and scope policy give the specific v0.8.0 boundary.
